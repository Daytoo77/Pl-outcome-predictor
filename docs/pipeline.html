A walk-through

From one match to the whole pipeline

You are predicting one of three things for every fixture, home win, draw or away win, from what was knowable at kickoff. This page starts with a single Arsenal match, shows how its features are built without cheating, then zooms out to the six stages that turn 25 seasons of results into a model you can trust.

Start with one concrete match

Arsenal v Stoke, 12 September 2015, at the Emirates. By the time this match kicks off, Arsenal have already played four league games this season. The model is not allowed to know the score (it will be 2–0). It is only allowed to know things that were already true at 15:00 UK time that Saturday.

Here is Arsenal's season so far, the four rows above the match we are predicting, and the one row we want a prediction for:

From those four prior matches the model computes its season-to-date features, for example:

  • pts_std, mean points this season = (0 + 3 + 1 + 3) / 4 = 1.75
  • gf_std, mean goals scored = (0 + 2 + 0 + 1) / 4 = 0.75
  • ga_std, mean goals conceded = (2 + 1 + 0 + 0) / 4 = 0.75

The last-five form feature reaches further back. Going into the Stoke match Arsenal's pts_roll5 was 2.0, because the five-game window still held the tail of 2014–15; on opening day against West Ham it had been 1.6. Stoke get the same treatment from their own prior games. The match becomes one row of home minus away differences, and the label H. Do that for every match across 25 seasons and you have a training table. The rest of this page is how that table is built and checked.

02

How a rolling feature is built

"Last-five form" sounds obvious, but the ordering of two operations is the whole game. You must shift by one match first, then average, so a row sees the five matches before it, never itself.

In the wildArsenal's real pts_roll5 going into that Stoke match was 2.0, and the model only ever sees the value before each match. The figure computed for the Stoke row would still read 2.0 even after Arsenal had won it.
03

Why data leakage happens

Leakage is when information from the future, or from the match itself, reaches the model at training time. It produces a model that looks superb in a notebook and barely beats a coin flip on next weekend's games. Two versions of the same experiment:

Subtle leak to watchEven with a season split, fitting anything on the whole dataset first and splitting after lets test-season statistics bleed into training. This project fits its expected-goals proxy and its odds-bias correction only on seasons up to 2018-19, and tunes every meta-parameter on the validation block that precedes the slice it is scored on.

05

Reading the confusion matrix

Once the model predicts on the held-out seasons, you cross-tabulate what actually happened against what the model said. Rows are the truth, columns the prediction. The diagonal is correct; everything off it is a specific kind of mistake. These are the real counts on the 699 test matches of 2023-24 and 2024-25.

How to read each row

  • Row "actual H": of 307 real home wins, the model got 248. It confused the rest with away wins (59), never with draws. Home wins are the easy class.
  • Row "actual A": similar story: 144 of 229 correct, the main confusion is with home wins.
  • Row "actual D": of 163 real draws, the model caught none. It called 98 of them home wins and 65 away wins. Under argmax, the model never predicts "draw".

Why draws are the weak point

Three reasons stack up:

  • Base rate. Draws are about a quarter of matches (24.7% across the dataset), the smallest class. A model minimising log loss holds the draw probability near that base rate, and a probability near 25% is almost never the largest of three.
  • No signature. Section 4 showed it: no pre-match feature correlates with a draw. A draw is often two well-matched teams plus a low-scoring game, and the second part is close to random.
  • Geometry. A draw sits between H and A in every feature that matters (Elo difference near zero, form difference near zero). Any small error pushes the prediction into the nearest decisive class.
What the project does about itNot class weights: an earlier version used them, and they pushed draw probabilities away from the true rate and made the log loss worse. Instead the model is judged on log loss, so a calibrated 30% draw probability earns credit even when the argmax is still H; the goal model (Dixon–Coles) supplies a draw probability that falls out of the scoreline arithmetic; and for a use case that needs draws called, a decision rule multiplies P(draw) by 1.75 before the argmax, a factor tuned on validation to reach 40% draw recall. That rule is reported, never trained on.

Where this sits in the build. explore.ipynb produces the clean table, features.ipynb produces the feature table with the columns shown in section 4, and model.ipynb does the season split from section 3, trains the models, and exports them. This page is the gentle version; how it works covers what the trained model actually does, and the report goes through the reasoning in full.
